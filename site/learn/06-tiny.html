失敗可能性観測する値考えられる原因・検証
特徴抽出P2/P3/P4/P5の応答・位置別特徴小物体の空間情報が残っているか

同じGTが検出されない場合でも、失敗箇所によって対策は変わります。入力解像度、stride 4のP2導入、Loss、割当、BBox表現をすべて一度に変えると、原因がわからなくなります。変更はA/B条件で分離してください。

2. 幾何候補：4pxでもGridは存在する

ここではYOLOX公式の get_geometry_constraint に見られる中心半径1.5を参照し、1GT・1スケールの候補抽出を再現します。実際のYOLOXはP3/P4/P5を合算して処理するため、このシミュレータは全SimOTAの一部分です。

grid_center = ((gx+0.5)·stride, (gy+0.5)·stride)
eligible = |grid_center_x − GT_cx| < 1.5·stride
　AND |grid_center_y − GT_cy| < 1.5·stride

例えばStride8では格子の参照中心は8pxごとですが、GTの幅が4pxでも中心近傍に候補を持てます。「Stride8だから4px未満のBBoxは表現できない」は誤りです。YOLOXの幅は対数で表現され、負のraw幅を使えばStrideより小さなBBoxを表せます。ただし、候補位置が存在することは高い特徴品質や十分なScoreを保証しません。

青い候補は中心制約を通過、緑（Score不足時は赤茶）はコストで選ばれた正例です。黄色は架空GT。右上の拡大図は数値説明用であり、元画像の解像度が上がったわけではありません。

3. IoU・SimOTA・Scoreを混同しない

候補のBBoxとGTのIoUが高くても、ObjectnessまたはClassificationが低いと検出Scoreは下がります。一方、SimOTAの内部では分類CostとIoU Costを組み合わせて正例を選択します。推論のScore閾値は正例割当そのものを変えません。

Score = sigmoid(obj_logit) · sigmoid(cls_logit)
classCost = BCE(√(sigmoid(obj)·sigmoid(cls)), positive_target=1)
IoUCost = −log(IoU+1e−8)
Cost = classCost + 3·IoUCost
Dynamic K = max(1, floor(sum(top10 IoUs)))

上記は1クラス・1GTの授業用簡略式です。公式コードでは全クラスのBCE、GTごとのCost行列、幾何制約違反への大きな罰則、複数GTとの競合解消があります。公式YOLOXの yolo_head.py のバージョンによって細部が異なり得るので、研究実験では必ずコミットを固定します。

自分の研究仮説

「幾何候補あり・最大IoU高・Objectness低」の状態で、BBox回帰式だけ変更すると検出Scoreは改善するでしょうか。答えは現段階では決まりません。候補数、BBox品質、信頼度を同じ画像で別々に記録する必要があります。

4. 4出力値の別の解釈を考案する

まず演習ページの記入欄に、独自のBBox表現を書いてください。次の定義は仮説提出後に読む解説として扱います。

比較解説を開く：YOLOXとSigned LTRB

YOLOX標準：中心と対数幅高さ

cx = (gx + tx)·stride,　cy = (gy + ty)·stride
w = exp(tw)·stride,　h = exp(th)·stride
x1 = cx−w/2,　x2=cx+w/2

局所微分 ∂w/∂tw=w。小さなGTを扱う際に、スケールと損失関数の組合せがどう勾配へ影響するかが研究対象です。w>0 は保証されます。

Signed LTRB：参照中心から辺までの符号付き距離

l = refx − x1,　t = refy − y1
r = x2 − refx,　b = y2 − refy
x1 = refx−l,　y1=refy−t
x2 = refx+r,　y2=refy+b
width = l+r,　height = t+b

参照中心がBBoxの外側でも、符号付きの値を使えば四辺を表現できます。ただし、raw4値を無制約で出力すると width≤0 や height≤0 という無効BBoxも生じます。境界順序をどう保証するか、Lossをどう設計するかが重要です。

順序保証付きの別案

cx = refx + dx, cy = refy + dy
w = softplus(uw) + ε, h = softplus(uh) + ε
x1 = cx−w/2, x2 = cx+w/2

これは四辺独立出力のSigned LTRBそのものではありませんが、常に正の幅・高さを保証します。どちらが学習に有利かは数式の形だけでは決まりません。同じ予測数値から算出したIoUを、改善率として使わないこと。

6. 後日、正式な画像とラベルを投入するために

現時点では実データを要求しません。教材構造が完成したら、ユーザーが用意する画像とBBoxラベルを取り込みます。その前提として、画像サイズ、BBox座標とカテゴリ、分割を固定するCOCO形式の受入契約を実装しました。

必要な入力

COCO JSONの images（id、file_name、width、height）、categories（id、name）、annotations（id、image_id、category_id、bbox=[x,y,w,h]、ignore、iscrowd）と、対応するPNG/JPEG画像です。1枚に複数の頭部・人物・ignore領域を許容します。bboxは原画像ピクセル座標です。Annotation JSONのカテゴリを勝手に再割当しません。

画像はtrain / val / testを別ファイルに分け、同じ画像のSHA-256が分割をまたいで出現しないことを検査します。ただし内容が視覚的にほぼ同じ近重複や人物単位のリークは別途監査が必要です。

python3 tools/unit06/dataset_contract.py \
  --images /private/dataset/train/images \
  --annotations /private/dataset/train/coco.json \
  --split train

python3 tools/unit06/dataset_contract.py \
  --images /private/dataset/val/images \
  --annotations /private/dataset/val/coco.json \
  --split val \
  --compare-manifest out/unit06/dataset_manifest_train.json

処理はローカルで完結し、画像内容はアップロードしません。出力先はデフォルトでGit管理対象外のout/unit06/です。公開用教材への自動変換・自動アップロードはありません。画像・ラベルの商用・再配布許諾、モデル重み、プライバシー・肖像権の確認を経た後、公開するサブセットとトレースを明示的に選びます。

現在の実装はCOCO JSONのみ対応です。YOLO txtなど別形式のラベルは、正式データを受け取った段階で変換層を設計します。検証ツールを通しても、アノテーション自体の品質や素材の利用権利を自動保証することはありません。
